### FUN-GROUP-005 詳細：招待URLからの参加フロー

招待URL（`/family/join?code=<inviteCode>`）にアクセスした際の挙動を認証状態ごとに定義する。

#### ケース別フロー

| ケース | フロー |
|---|---|
| **ログイン済み・グループ未参加** | 参加確認画面を表示 → 「参加する」でグループ参加 → `/family` へ遷移 |
| **ログイン済み・グループ参加済み** | 参加確認画面をスキップし `/family` へ直接リダイレクト |
| **未ログイン（既存アカウント）** | `/login?next=/family/join?code=<inviteCode>` へリダイレクト → ログイン後に参加確認画面へ戻る |
| **未ログイン（新規ユーザー）** | `/login?next=...` → 「新規登録はこちら」で `/register?next=...` → 登録後 `/profile?next=...` → プロフィール設定後に参加確認画面へ戻る |
| **招待コードが無効/期限切れ** | 参加確認画面でエラーメッセージを表示 |

#### `?next=` パラメータによるURL引き継ぎ

未ログインユーザーが保護ルート（`/family/*`）にアクセスするとミドルウェアが以下の形式でログイン画面へリダイレクトする。

```
/login?next=%2Ffamily%2Fjoin%3Fcode%3D<inviteCode>
```

ログイン・新規登録・プロフィール設定の各画面は `next` パラメータを受け取り、処理完了後にそのURLへリダイレクトする。新規登録時は `/profile?next=...` として引き継ぎ、全フロー完了後に参加確認画面へ戻る。

#### RLSとAPIエンドポイントの設計

`groups` テーブルのRLSポリシーは「自分が所属するグループのみ参照可能」に制限されており、グループ未参加ユーザーは `anon` キーで招待コードを検索できない。このため、参加前のグループ情報プレビューは **NestJS API（`service_role` キー）経由** で取得する。

```
GET /v1/groups/join/preview?inviteCode=<code>
  → service_role キーで RLS をバイパス
  → グループ名・メンバー数を返す（認証必須、ロール制限なし）

POST /v1/groups/join
  → { inviteCode } を受け取りグループメンバーに追加
  → 成功後フロントで supabase.auth.refreshSession() を呼び JWT を更新
```

#### 参加後のJWT更新

グループ参加後、JWTの `family_group_id` クレームを更新するためフロントエンドで `supabase.auth.refreshSession()` を呼び出す。Supabaseのカスタムアクセストークンフックが `group_members` テーブルから最新の `family_group_id` を取得してJWTに埋め込む。

### FUN-TASK-001 詳細：担当者（assigneeId）の登録

- 親が子を `assigneeId` として指定できる（必須ではないが、指定することで担当者フィルタ・報酬集計が有効になる）
- 登録画面では子メンバーがいる場合、担当者セレクトボックスが表示され**必須**入力となる
- 指定する担当者は同一ファミリーグループのメンバーであること。グループ外ユーザーを指定した場合は 403 エラー

### タスクステータス遷移

```
[未対応] → （子が報告）→ [対応済]
[対応済] → （親が承認）→ [完了]（報酬確定）
[対応済] → （親が差し戻し）→ [未対応]
[対応済] → （子が取り下げ）→ [キャンセル済]
[未対応] → （子が取り下げ）→ [キャンセル済]
[未対応] → （親が即時完了）→ [完了]（報酬確定）★
[未対応/対応済] → （期限超過）→ [期限切れ]
```

> ★ **即時完了（「既に完了にする」）**: 親がタスク編集画面の「既に完了にする」チェックボックスをオンにして更新すると、子の実行報告ステップをスキップして `未対応` から直接 `完了` に遷移させることができる。  
> タスクに `assignee_id`（担当者）が設定されている場合、`task_completions` レコードを自動生成して即時承認状態にする（`reported_at` と `approved_at` に同一の操作日時を設定）。これにより報酬明細・報酬合計金額の集計に通常の承認と同様に反映される。  
> `assignee_id` が未設定のタスクを即時完了した場合は `task_completions` レコードが作成されないため、報酬集計の対象外となる。  
> **制約（paid 済み月のブロック）**: 当月（JST）の報酬が `paid` 済みの場合、**即時完了**および**通常の承認（対応済 → 完了）**のいずれも実行できない（400 エラー）。`paid` 後に `task_completions` の `approved_at` を設定しても当月の集計は再計算されず、翌月の集計範囲（`approved_at` ベース）にも含まれないため、双方の操作をブロックする。

> ステータスの英語値（schema.dbml / OpenAPI）: `pending`（未対応）/ `reported`（対応済）/ `completed`（完了）/ `cancelled`（キャンセル済）/ `expired`（期限切れ）。  
> 「差し戻し」はステータスではなく遷移アクション（対応済 → 未対応）であり、独立したステータス値は存在しない。

### ステータス遷移別 task_completions 操作

各ステータス遷移時に `task_completions` テーブルに対して行われる操作を以下に示す。

| 遷移 | アクター | task_completions 操作 |
|------|---------|----------------------|
| 未対応 → 対応済（報告） | 子 | INSERT（`reported_at` = 操作日時、`approved_at` = NULL） |
| 対応済 → 完了（承認） | 親 | UPDATE（`approved_at` = 操作日時、`approved_by` = 親ID）。当月報酬が `paid` 済みの場合は 400 エラー |
| 対応済 → 未対応（差し戻し） | 親 | ソフトデリート（`deleted_flag = true`） |
| 未対応 → 完了（即時完了）★ | 親 | INSERT → 即時 UPDATE（assignee あり時のみ。`reported_at` と `approved_at` を同一の操作日時で設定） |
| 未対応 → キャンセル済 | 子 | ソフトデリート（完了記録が存在しない場合は操作なし） |
| 対応済 → キャンセル済 | 子 | ソフトデリート |

| 種別 | 説明 | 例 |
|------|------|-----|
| 定量目標（回数） | 指定回数以上の実行 | 「月15回以上ゴミ出しをする」 |

### FUN-GOAL-003 詳細：担当者（assigneeId）と担当者不一致バリデーション

- 子メンバーがいる場合、担当者セレクトボックスが表示され**必須**入力となる
- 指定する担当者は同一ファミリーグループのメンバーであること。グループ外ユーザーを指定した場合は 403 エラー
- `taskId`（紐付けタスク）と `assigneeId` を両方指定した場合、タスクの `assignee_id` と目標の `assigneeId` が一致するか検証する
  - 不一致の場合: HTTP 400 / `{ code: "ASSIGNEE_MISMATCH", message: "タスクの担当者と目標の担当者が一致しません" }`
  - フロントエンドでも事前チェックを行い、モーダルでタスクを検索する際に担当者未選択の場合はエラーを表示してモーダルを開かない
  - 担当者を変更した際は選択済みのタスクをリセットする（不整合防止）

### FUN-GOAL-001 / FUN-GOAL-003 共通：ロール別フィルタ挙動

| ロール | タスク一覧 / 目標一覧 | 担当者フィルタUI |
|--------|----------------------|-----------------|
| 親 | 全メンバー分を表示（デフォルト） | セレクトボックスで担当者を絞り込める |
| 子 | 自分の分のみ自動表示（APIで強制フィルタ） | 非表示 |
